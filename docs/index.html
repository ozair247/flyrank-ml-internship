Refresh & Content
Opportunity Scoring

Can a learned model prioritize which pages to review before a hand-written rule can?

Author — Ozair Malik Lane — 2, Refresh / Content Opportunity Scoring Date — 28 Aug 2026
Abstract

We ask whether a learned model can prioritize content refresh candidates better than a hand-written rule, using only search performance and content metadata from a single month. The analysis uses 9.8 million daily search rows from March 2026, aggregated to 176,000 content-item records, with features spanning age, impressions, CTR, average position, and engagement. A Random Forest trained on these features and evaluated on a client-grouped, held-out split achieves Precision@50 of 0.56, against 0.04 for the Week-4 baseline rule — a 52-percentage-point improvement. The model's output is converted into a ranked action queue with reason codes, intended to help a content strategist decide which pages to review first. All findings are directional and decision-support only; no production claims are made.

01

Problem framing

Decision supported: which pages should a content strategist review for refresh first, given limited editorial time and resources.

Unit of analysis: one content item per client, aggregated over a calendar month.

Output: a ranked list (score) with action labels and reason codes.

Human action: start at rank 1 and review the page for possible content refresh, metadata updates, or consolidation. Actions are never automated; every recommendation requires human judgment.

Cost of a wrong call: a false positive wastes editorial time on a page that does not need a refresh; a false negative lets a declining page go unnoticed, risking further traffic loss.

Why data/ML helps: the signal space — age, impressions, position, CTR, engagement — is small and interpretable, but a simple rule cannot capture non-linear interactions (staleness matters most when a page is still visible). A learned model can combine these signals more flexibly and produce a calibrated risk score.

02

Data safety

Data used

  • fact_content_daily_performance — partitioned, month=2026-03
  • dim_content — content metadata
  • dim_clients — history start dates, used only for availability checks

Columns deliberately excluded

  • impr_last15, impr_prev15 — the label's own ingredients; using them as features would be leakage.
  • gsc_sum_position — redundant with gsc_avg_position, adds no independent signal.
  • All raw URL, keyword, and client identifiers — kept hashed; never used as features.
  • health_score, priority_score, action_type — product decision outputs that must not be learned from.

Leakage risks considered

  • Future-window columns (impr_last15, impr_prev15) were never included in the feature set.
  • Pseudonymous IDs (client_hash_id, content_hash_id) were used only for grouping and joining, never as model features.
  • No client-identifying information appears anywhere under work/.
03

Baseline

Transparent rule:

score = (content_age_days >= 180) × (impressions_month >= 500) × impressions_month

Why it is a fair comparison:

  • It uses only two signals that are available before the decision moment.
  • It produces a ranking in the same format as the model — higher score, higher review priority.
  • It was evaluated on the same client-grouped test split as the model.

04

Model / analysis

Method: Random Forest classifier — 300 trees, max depth 6, min samples per leaf 20, random_state=42.

Why it fits the lane:

  • The label is binary (is_declining_proxy), and a probability is needed to rank.
  • Random Forest can express non-linear interactions — staleness mattering only at certain traffic levels, for example.
  • It is more interpretable than gradient boosting, and easier to explain to stakeholders.

Feature list

content_age_daysDays since content creation.
impressions_monthTotal Google Search Console impressions in March.
ctr_monthClicks ÷ impressions × 100.
avg_position_monthAverage GSC position — zero-values (no data) removed before averaging.
engagement_rate_monthGA4 engaged sessions ÷ sessions × 100; zero where no sessions.
has_ga4_month1 if any GA4 data is available that month, else 0.
word_countWord count of the content; missing filled with 0.
has_word_count1 if word count is present, else 0.

Left out on purpose

  • clicks_month — highly correlated with impressions; adds nothing for ranking.
  • sessions_month, engaged_sessions_month — raw counts already represented by the engagement rate.
  • impr_last15, impr_prev15 — label ingredients (leakage).
  • Content type, intent, keyword metrics — excluded to keep the model simple and focused on performance signals.

Target definition

is_declining_proxy = 1 if impr_prev15 > 0 and impr_last15 < 0.8 × impr_prev15; else 0.

05

Evaluation

Split: grouped by client_hash_id — 70% train, 30% test — using GroupShuffleSplit with random_state=42.

Why grouped: pages from the same client share a template, vertical, and team. A random split would leak client information from train to test and inflate scores.

Error analysis

Among the model's top 50 predictions, 22 are false positives. They cluster in two age bands: 5 under 90 days, 17 between 180–365 days. The three highest-confidence false positives all share impressions_month = 1 and ctr_month = 0 — pages with no prior traffic baseline. The proxy label cannot mark them as declining because there is nothing to decline from; the model reads staleness as decline risk even when traffic is near zero.

22 of 50 is a real limitation, not noise — nearly half the model's own top picks miss on this proxy label.
06

Interpretation

Top features by permutation importance

  1. content_age_days (0.066) — older pages are more likely to be flagged as declining; matches the baseline's staleness idea.
  2. impressions_month (0.036) — visible pages are more likely to show a decline signal.
  3. avg_position_month (0.021) — lower positions (worse ranking) correlate with decline risk.

Surprises & negative results

Negative result Very old pages (365+ days) actually have a lower decline rate than middle-aged pages (90–180 days). Age alone is not monotonic — staleness matters, but only up to a point.
Negative result Low CTR among top-ranking pages is not associated with higher decline risk. This was counterintuitive, and means the original "CTR-fix" flag from earlier lanes may be misaligned with actual decline.

Key insight: the model's value comes from balancing staleness against visibility and recent ranking signals — exactly the balance a fixed rule cannot strike.

Recommendation

The model's score converts into a ranked action queue with three labels:

review_for_refresh
Top-decile risk, with ≥500 impressions.
monitor
High risk but low traffic, or moderate risk with visible traffic.
no_action
Low risk, or invisible.
↓ Download the full ranked queue (CSV)

How a FlyRank editor would use it tomorrow: start at rank 1, review the page — is it live? is the decline seasonal? is an update already scheduled? — and only then decide whether to refresh content, update metadata, or leave it as is. Every item must pass a human check; the model is decision-support, not an automated system.

Confidence and limits: on the held-out client split, Precision@50 is 0.56, but this rests on a single month and a proxy label. I would not recommend using the model on a new client, or a different time period, without retraining. False positives on near-zero-traffic pages are the biggest risk; a simple pre-filter would likely improve precision further.

Suggested pre-filter:
impr_prev15 ≥ 10
would drop most of the zero-traffic false positives identified in §5.
